# Apache Ignite Vector Index

Проект выполнен в рамках **летней стажировки СберЛаб-НГУ 2026**.

**Apache Ignite Vector Index** - прототип векторного индекса для распределённой базы данных Apache Ignite. Он позволяет выполнять быстрый приближённый поиск ближайших векторов прямо поверх данных Ignite, без отдельной векторной базы данных.

Прототип реализован на Apache Ignite 2.18 без изменения исходного кода базы данных, с использованием её API.
## О проекте

Apache Ignite распределяет данные между узлами кластера, но встроенного векторного поиска в нём нет. Поэтому для работы с векторами обычно приходится использовать отдельную систему вроде Qdrant или Milvus и синхронизировать её с основной БД.

В этом проекте реализован другой подход: **данные и векторы хранятся в Apache Ignite, а индекс для быстрого поиска работает непосредственно на серверных узлах кластера.**

Прототип поддерживает:

- приближённый поиск ближайших векторов; 
- распределённый поиск по нескольким узлам; 
- отдельный индекс для каждой основной партиции данных; 
- автоматическую синхронизацию индекса с данными Apache Ignite; 
- добавление и удаление векторов; 
- поиск по свежим данным без ожидания полной перестройки индекса; 
- фоновую перестройку и восстановление индекса; 
- частичный результат при временной недоступности части узлов (отказоустойчивость); 
- метрики состояния кластера и локальных индексов.

## Архитектура

```text
                    Search request
                          │
                          ▼
                  Search Aggregator
                          │
              ┌───────────┼───────────┐
              ▼           ▼           ▼
	        Node         Node        Node
              │           │           │
          local index   local index   local index
              │           │           │
          local top-k   local top-k    local top-k
              └───────────┼───────────┘
                          ▼
                     global top-k
                          │
                          ▼
                     Ignite Cache
```

Apache Ignite сам распределяет данные между узлами. Индекс следует этому распределению: каждый сервер хранит индексы только для тех частей данных, за которые он отвечает.

Выделенного координатора в кластере нет. Агрегатор работает на каждом серверном узле, поэтому поисковый запрос может быть обработан через любой из них.
### Индекс на партицию

Данные Ignite разбиваются на **партиции** - части общего набора данных, распределённые между узлами.

Для каждой `PRIMARY`-партиции создаётся отдельный локальный векторный индекс.

Если после подключения или отключения узла происходит ребаланс и PRIMARY-партиция переезжает, её индекс строится заново на новом владельце.

BACKUP-партиции отдельно не индексируются. Если такая партиция становится PRIMARY, для неё строится локальный индекс.

### Кэш как основной источник данных
Ключевая идея нашей архитектуры заключается в том, что индекс - производная кэша. Все исходные данные хранятся в кэше. Векторный индекс при необходимости полностью восстанавливается из кэша.

```text
Cache update
     │
     ▼
Cache event
     │
     ▼
Чтение актуального значения
     │
     ▼
Обновление локального индекса
```

Сначала изменяется запись в кэше, затем обновляется индекс. Поэтому между ними может быть небольшая задержка.

Если обновление индекса завершилось ошибкой, индекс соответствующей партиции можно восстановить из кэша. Дополнительно система периодически проверяет состояние партиций.

## JVector

Для быстрого поиска используется **JVector**, работающий внутри JVM.

В проекте есть два варианта поиска для сравнения производительности:

- **JVector** - быстрый приближённый поиск по графовому индексу;

- **BruteForce** - точный полный перебор, используемый как эталон для сравнения скорости и качества.
### Обновление индекса

Чтобы не перестраивать граф после каждой вставки, новые векторы сначала попадают в буфер свежих данных и сразу участвуют в поиске.

```text
               Search
                  │
          ┌───────┴───────┐
          ▼               ▼
     JVector graph     Hot buffer
          │               │
          └───────┬───────┘
                  ▼
               Result
```

После накопления изменений новая версия графа строится в фоне и заменяет предыдущую.

Для удаления используются tombstone-маркеры: объект сразу исключается из поиска, а окончательно удаляется из структуры при следующей перестройке.

## Распределённый поиск

Единого графа на весь кластер нет. Каждый сервер ищет только по своим PRIMARY-партициям.

```text
query
 │
 ├── Node 1 -> local top-k
 ├── Node 2 -> local top-k
 └── Node 3 -> local top-k
 │
 ▼
merge
 │
 ▼
global top-k
```

Локальные результаты объединяются, сортируются по расстоянию, после чего выбираются **top-k** результатов для всего кластера.

Для сравнения используется косинусное расстояние, так было прописано в документации OpenAI CLIP, который мы использовали для создания эмбеддингов.

Найденные ID дополнительно проверяются через Ignite Cache, поэтому уже удалённый объект не попадёт в результат, даже если старая версия графа ещё содержит его.

## Отказоустойчивость

Потеря локального индекса не приводит к потере данных, их исходная версия остаётся в Ignite Cache.

После отключения или возвращения узла Apache Ignite перераспределяет PRIMARY-партиции. Прототип отслеживает новое распределение и при необходимости строит недостающие индексы заново.

Если часть серверов временно недоступна или не успела ответить вовремя, поиск может вернуть данные от доступных узлов и пометить ответ как неполный.

Для распределённого запроса установлен общий лимит времени ожидания. Если часть узлов не отвечает вовремя, результат возвращается с признаком `partial`.

Для демонстрации был реализован семантический поиск изображений.

     ▼

     │
     ▼

     │
     ▼

     │
     ▼

     │
     ▼

Модель **CLIP ViT-B/32** преобразует текст и изображения в одно 512-мерное векторное пространство. Благодаря этому можно искать изображения как по другой картинке, так и по текстовому описанию.

В демонстрационном наборе использовалось **608 тысяч векторов**.

## Бенчмарки

JVector сравнивался с точным поиском **BruteForce**.

`recall@k` показывает, какую долю результатов точного поиска удалось найти приближённому алгоритму. Например, `recall@10 = 96%` означает, что JVector в среднем находит около 96% объектов из точного top-10.

### Скорость поиска

|Векторов|k|BruteForce|JVector|Ускорение|Recall|
|--:|--:|--:|--:|--:|--:|
|260k|10|49.9 ms|7.7 ms|6.5x|97.3%|
|450k|10|83.9 ms|7.9 ms|10.6x|96.1%|
|608k|10|96.3 ms|7.4 ms|**13.0x**|96.3%|

На наборе из **608 тысяч 512-мерных векторов** JVector выполнял поиск примерно в **13 раз быстрее полного перебора** при `recall@10` около **96%**.

### Нагрузочное тестирование

|Клиентов|Запросов/с|Среднее время ответа|
|--:|--:|--:|
|1|200|5 ms|
|2|366|6 ms|
|4|500|8 ms|
|8|590|14 ms|
|16|622|26 ms|
|32|623|51 ms|

Пропускная способность выходит на плато примерно в **620 запросов в секунду**. Дальнейшее увеличение числа клиентов в основном увеличивает время ответа.

### Профилирование

Профилирование через **Java Flight Recorder** показало, что основная вычислительная нагрузка приходится на вычисление косинусной близости.

Сеть, Apache Ignite и сборщик мусора не были основными узкими местами, поэтому одно из направлений дальнейшей оптимизации - ускорение вычисления расстояний между векторами, например с помощью SIMD.
